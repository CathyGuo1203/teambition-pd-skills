# WBS 拆解规则与标准

本文件定义了将项目需求拆解为 WBS（Work Breakdown Structure）时的核心标准和逻辑。在执行 `wbs-planner-tb` 技能的"智能 WBS 拆解"阶段时，必须严格遵循以下规则。

## 1. 三层结构定义

| 层级 | 定义 | 负责人 | 在 Teambition 中的映射 |
| --- | --- | --- | --- |
| **Roadmap** | 项目整体时间线和目标，规划所有 Epic 的优先级。 | 项目经理 / PM | 项目本身或里程碑 |
| **Epic** | 大功能模块或阶段，包含多个 Task。 | PM 规划 | 任务分组 / 父任务 |
| **Task** | 可分配给单人、1-2 个工作周期内完成的具体任务。 | PM 创建，Dev 执行 | 具体任务 (Task) |

## 2. Task 粒度标准 (核心)

这是整个拆解体系的核心。Task 拆得不够细，验收就容易失败。一个合格的 Task 必须同时满足以下四个条件：

1. **单一交付物**：只做一件事，只验收一件事。
2. **验收可量化**：条件具体到操作步骤，不能是"看起来不错"或"功能正常"。
3. **体量可控**：预计 1-2 个工作周期（通常为 1-2 人天）内完成，超过则必须继续拆分。
4. **独立可测**：不依赖未完成的其他 Task。

**判断示例：**
- ❌ "实现农场系统" → 这是 Epic，不是 Task。
- ❌ "优化页面" → 没有明确的验收标准。
- ❌ "完成种植和收获" → 两件事，应拆分为两个 Task。
- ✅ "实现 7 块农田网格布局，点击地块高亮" → 合格的 Task。
- ✅ "接入 Google OAuth，登录后显示用户头像" → 合格的 Task。

## 3. 拆解思路与步骤

拿到一个 Epic 后，按以下顺序思考并生成 Task：

1. **明确终态**：这个 Epic 的最终交付物是什么？
2. **识别功能点**：要达到终态，需要哪些独立的功能点？每个功能点就是一个候选 Task。
3. **校验体量**：每个候选 Task 能否在 1-2 个工作周期内完成？不能则继续拆分。
4. **校验边界**：每个 Task 能否独立验证？不能则调整边界或合并。

## 4. 常见错误与修正

| 错误现象 | 后果 | 修正方案 |
| --- | --- | --- |
| 一个 Task 包含多个功能点 | 验收时部分通过部分不通过，扯皮 | 拆分成多个独立的 Task |
| 验收条件写"功能正常" | Dev 和 PM 对"正常"理解不同 | 写具体操作步骤和预期结果 |
| Task 之间有隐含依赖 | 后面的 Task 因前面没做完而卡住 | 明确依赖关系或调整执行顺序 |
| 工作量估计过大 | Dev 长时间无产出，风险不可控 | 拆到每个 Task 有阶段性产出 |
